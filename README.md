# ag-mcp-gateway

Локальный standalone-шлюз для MCP-инструментов. Один процесс поднимает Streamable HTTP, страницу каталога и метрик и отдельный журнал выбранного профиля. Клиенты с транспортом stdio подключаются через лёгкий адаптер к тому же процессу.

## Быстрый старт

Из каталога распакованной сборки:

```sh
./ag-mcp-gateway demo-profile
./ag-mcp-gateway serve --allow-unauthenticated
```

Откройте [дашборд](http://127.0.0.1:18792/) или выполните во втором терминале:

```sh
./ag-mcp-gateway status
./ag-mcp-gateway logs --limit 20
./ag-mcp-gateway config codex
```

Профиль `demo` запускает встроенный тестовый MCP. В каталоге есть разрешённый `demo.echo` и запрещённый `demo.blocked`. Для демонстрации вызовите `demo.echo` через клиент. После первого запуска `demo-profile` можно пропускать. Для журнала одного MCP используйте `logs --backend demo`.

## Профиль компании

В публичных исходниках хранятся синтетические шаблоны. Рабочие корпоративные профили, журналы и состояние размещаются в отдельном каталоге оператора.

1. Скопируйте [пример профиля](profiles/company.example.json) в `~/.ag-mcp-gateway/profiles/company.json` или выберите каталог через `--profiles`.
2. Замените адреса и команды на доверенные. Для stdio используйте абсолютный путь к исполняемому файлу. Для токенов укажите ссылки `access_token_keychain` и `bearer_token_keychain` или явно задайте переменные окружения. `env_from` передаёт указанные переменные локальному stdio MCP.
3. Запустите `./ag-mcp-gateway --profile company serve`. Параметры `--profiles`, `--profile`, `--state` и `--port` указываются перед командой.
4. Адрес MCP для этого профиля — `http://127.0.0.1:18792/mcp/company`. HTTP-клиенты используют Bearer. Для дашборда браузер запрашивает логин `gateway` и токен в качестве пароля.

Профиль — доверенная конфигурация оператора. Команды stdio выполняются с правами пользователя шлюза. Передавайте другим компаниям архив сборки и шаблоны профилей без секретов и локальных журналов. Для параллельной работы разных компаний запускайте отдельные процессы на разных портах с разными токенами и каталогами состояния. Один процесс обслуживает одну общую учётную запись upstream на сервер. Пользователи одного профиля разделяют доступ к разрешённым инструментам.

`denied` проверяется при вызове и исключает инструмент из MCP-каталога. Дашборд показывает его оператору. В `singleflight` перечисляйте только операции чтения, безопасные для одновременных запросов от клиентов профиля с одинаковыми аргументами. Объединение действует до завершения текущего вызова. Следующий вызов снова идёт к серверу. Вызовы с MCP-метаданными проходят отдельно. Шлюз передаёт поля расширений upstream, а токен прогресса остаётся в сессии клиента. Изменения профиля вступают в силу после перезапуска.

## Тестовый и production MCP

Возьмите [шаблон test](profiles/company-test.example.json) и [шаблон production](profiles/company-prod.example.json). Сохраните их как `company-test.json` и `company-prod.json` в выбранном каталоге профилей. Замените синтетические адреса и укажите отдельные переменные для токенов шлюза и upstream MCP каждой среды.

Запустите два профиля в отдельных терминалах:

```sh
./ag-mcp-gateway --profile company-test serve
./ag-mcp-gateway --profile company-prod serve
```

| Профиль | MCP-адрес по умолчанию |
| --- | --- |
| Test | `http://127.0.0.1:18793/mcp/test/company-test` |
| Production | `http://127.0.0.1:18794/mcp/production/company-prod` |

В JSON укажите `"environment": "test"` или `"environment": "production"`. Порт выбирается в порядке `--port`, `listen_port` в JSON, затем значение по умолчанию для среды. У старого профиля без поля `environment` сохраняются порт 18792 и адрес `/mcp/<profile>`. Для двух компаний в одной среде задайте разные порты. Если добавляете среду в существующий профиль, обновите клиентскую конфигурацию: изменятся адрес и путь для новых журналов.

Production требует `access_token_keychain` или `access_token_env` и отклоняет `--allow-unauthenticated`. Выбранный профиль обращается только к MCP, перечисленным в нём. У сред отдельные процессы, журналы, метрики и маршруты. Шлюз не переключается на другую среду, если выбранный MCP недоступен. Команда `config` выдаёт отдельное имя регистрации для каждой среды, поэтому обе записи можно включить в одном клиенте.

```sh
./ag-mcp-gateway --profile company-test config codex
./ag-mcp-gateway --profile company-prod config codex
```

## Повторное подключение HTTP Basic на macOS

Для MCP с HTTP Basic включите `"basic_keychain": true` у нужного HTTP-backend и задайте `access_token_keychain` или `access_token_env` на уровне профиля. В [примере Grafana](profiles/company-basic.example.json) уже есть эта структура. Используйте фактический адрес Streamable HTTP MCP. Режим `basic_keychain` и ссылки на Bearer-токен взаимоисключающие.

1. Запустите профиль и откройте дашборд. В браузере укажите имя `gateway` и тот же токен профиля, который MCP-клиенты передают как Bearer.
2. Откройте **Учётные данные MCP**, введите логин и пароль сервера, нажмите **Проверить и сохранить**.
3. Шлюз отправит HTTP Basic на заданный upstream, проверит MCP `initialize` и `tools/list`, сохранит запись в Связке ключей macOS и переключит только этот сервер. При отказе проверки или записи сохранятся прежняя запись и соединение. Если проверенная сессия закроется во время записи, шлюз оставит прежнее подключение и предложит повторно подключиться с сохранёнными данными.
4. Кнопка **Подключиться с сохранёнными данными** повторно открывает соединение с записью из Связки ключей. При следующем старте шлюз читает её автоматически.

Basic-логин и пароль общие для всех вызовов выбранного MCP через профиль. Запись Связки ключей привязана к пути файла профиля, среде, имени backend и его URL. При переносе профиля или смене адреса введите учётные данные заново. Начатые вызовы завершаются на прежнем соединении, новые идут через проверенную сессию. Если изменился список инструментов, обновите каталог в MCP-клиенте.

## Каталог MCP и контекст сессии

Дашборд группирует инструменты по серверу, показывает число доступных инструментов и даёт прямой переход к переавторизации. Отметка **Подключён** появляется после MCP `initialize` и успешного `tools/list`. Локальный stdio без входа через шлюз отмечен отдельно. Каталог различает отклонённые учётные данные (HTTP 401), запрет доступа (HTTP 403), неверный адрес, сетевую ошибку и некорректный ответ MCP. Рядом со статусом показано время последнего вызова, отправленного этому MCP с запуска шлюза, в UTC.

По умолчанию шлюз начинает принимать запросы после первичной проверки всех MCP. Для необязательного сервера можно задать `"background_startup": true` в его записи в `backends`. Такой сервер проверяется параллельно, пока обзор и готовые серверы уже доступны. В каталоге он виден со статусом **Проверяем подключение**. После проверки появятся его инструменты или причина сбоя. Если клиент загрузил каталог до завершения проверки, обновите список инструментов в клиенте или переподключите шлюз.

Для Basic можно ввести логин и пароль или вставить готовую строку Basic/Base64 для уже заданного в профиле адреса. Результат проверки виден в карточке выбранного сервера. Если проверка новых данных не удалась, статус действующего соединения остаётся виден отдельно.

Для локального MCP укажите команду, `args` и при необходимости `env_from`. Поле `session_args` задаёт соответствие между полями контекста и аргументами конкретных инструментов. Шлюз заполняет только пропущенные аргументы, объявленные в схеме инструмента. `forward_session_context: true` дополнительно передаёт зарезервированную MCP-метку `_meta["ag-mcp-gateway/session"]` локальному серверу. Оба параметра доступны для stdio и loopback HTTP.

[Пример профиля ag-tasks](profiles/local-ag-tasks.example.json) подставляет `harness`, `instance_id` и `remote_session_id` в `tasks_resolve_conversation`. Используйте актуальные значения от запускающего агента. Передача контекста помогает найти зарегистрированную привязку чата. Создание привязки и рабочая аренда идут через отдельные инструменты ag-tasks.

```sh
./ag-mcp-gateway --profile local-ag-tasks config codex \
  --harness codex --instance-id workstation-a --session-id actual-chat-id
./ag-mcp-gateway session-tag --harness codex --instance-id workstation-a --session-id actual-chat-id
./ag-mcp-gateway --profile local-ag-tasks logs --session-tag TAG
```

Сгенерированный фрагмент с заданным идентификатором относится к одной сессии. Клиент с прямым HTTP может передавать контекст в `_meta` каждого вызова. Поддерживаются `harness`, `instanceId`, `remoteSessionId` и `conversationId`. Требуется `remoteSessionId` или `conversationId`. Журнал хранит короткий хеш, который можно вычислить той же командой `session-tag`. Эти идентификаторы относятся к учёту работы. Авторизация и ключи рабочей аренды задаются отдельно.

## Горячее переподключение

В каталоге профиля с токеном нажмите **Переподключить** у нужного MCP. Через управляющий Bridge то же действие выполняет `gateway_reconnect_mcp` с именем сервера. Шлюз открывает новую stdio или HTTP-сессию с настроенной авторизацией, выполняет `initialize` и получает полный `tools/list`. Только после этого он переключает маршруты. Начатые вызовы завершаются на старой сессии. Если проверка не удалась, рабочее подключение остаётся доступно.

Уведомление upstream `notifications/tools/list_changed` запускает повторное чтение списка на текущей сессии. Неуспешное чтение сохраняет предыдущий каталог, пока соединение остаётся рабочим. Клиент получает актуальные схемы при следующем `tools/list`. Если он кэширует инструменты, обновите каталог клиента. Шлюз не посылает уведомления downstream по stateless HTTP.

## Корреляция вызовов

Для `tools/call` шлюз принимает W3C `traceparent` версии `00` и необязательный `tracestate` (до 32 записей и 512 символов). При прямом HTTP передайте эти заголовки или одноимённые поля в MCP `params._meta`. Явные HTTP-заголовки имеют приоритет. Для stdio передайте поля через `params._meta`.

Чтобы передать контекст дальше, добавьте `"forward_trace_context": true` в запись нужного MCP в `backends`. HTTP-сервер получает заголовки вызова и MCP-метаданные, stdio-сервер получает MCP-метаданные. Шлюз сохраняет исходную трассу даже без OpenTelemetry, не создаёт новую и выполняет вызовы с контекстом по отдельности.

Журнал сохраняет только `trace_id` и, если он задан, независимый тег сессии. Найти вызовы можно командой `ag-mcp-gateway --profile company logs --trace-id TRACE_ID`. Фильтры `--backend` и `--session-tag` можно комбинировать.

## MCP Bridge и секреты ОС

Добавьте `"management_bridge": true` в профиль с токеном шлюза и перезапустите его. Отдельная страница **Настройки** показывает текущую ревизию политики, список инструментов и источники учётных данных. Управляющий каталог можно подключить отдельно от рабочих инструментов:

```sh
ag-mcp-gateway --profile company config codex --management
```

Команда `mcp-bridge` открывает управляющий MCP по stdio. Прямой Streamable HTTP доступен по `/manage/<профиль>` или `/manage/<среда>/<профиль>` с тем же Bearer-токеном шлюза. Агент использует `gateway_inspect` для чтения состояния и ревизии, `gateway_set_tool_policy` для установки `allow`, `deny` или `singleflight`, `gateway_reconnect_basic` для подключения с уже сохранёнными Basic-данными. Singleflight, добавленный через Bridge, действует, пока инструмент объявлен доступным только для чтения. Устаревшую ревизию нужно перечитать. Политика применяется сразу, сохраняется в каталоге состояния профиля и переживает перезапуск. После смены политики клиент может обновить список инструментов. Включайте управляющий Bridge для агентов, которым вы делегируете эти изменения.

Для хранения токена в Связке ключей macOS выполните `ag-mcp-gateway token-set company-gateway` в терминале и введите значение в скрытом поле. В профиле укажите `"access_token_keychain": "company-gateway"`. Для Bearer upstream используйте `"bearer_token_keychain": "company-upstream"` в записи MCP. Профили содержат только имена записей. Basic вводится через страницу учётных данных.

При настроенной ссылке шлюз сначала читает запись ОС. Если записи нет или провайдер отсутствует, используется окружение только при явно заданном `access_token_env` или `bearer_token_env`. Ошибка доступа к записи ОС завершает проверку. Старые профили с одной ссылкой на окружение продолжают работать. Сейчас нативный провайдер — macOS Keychain. После замены токена перезапустите соответствующее подключение или процесс шлюза. MCP Bridge не принимает и не возвращает значения секретов.

## Реестр MCP skills и кэш подходов

Добавьте в профиль с токеном шлюза и включённым `management_bridge` параметр `"skill_router": {}`, затем перезапустите шлюз. База `skills.sqlite3` создаётся в каталоге состояния выбранного профиля. Тестовый и продовый профили используют отдельные базы.

- `gateway_skill_search` ищет по заголовкам и резюме. Сначала идут навыки с доступными инструментами, затем остальные. Внутри каждой группы учитываются полнотекстовая релевантность SQLite FTS5 и оценки полезности. Кэш ранжируется по совпадениям слов. При отсутствии подходящего доступного навыка ответ содержит `suggest_skill_draft: true`.
- `gateway_skill_load` выдаёт инструкции утверждённого навыка. В результатах поиска и загрузки видны недоступные и запрещённые инструменты. Агент сам решает, какие вызовы выполнить.
- `gateway_skill_propose` создаёт черновик. Оператор просматривает его и утверждает по ID. `gateway_skill_rate` добавляет оценку полезности после применения.
- `gateway_skill_cache_save` явно сохраняет обезличенные заголовок, резюме и порядок MCP-инструментов, включая повторы. Шлюз не собирает промпты, аргументы и результаты автоматически. Удаляйте чувствительные сведения из текста перед отправкой черновика или записи кэша.

```sh
ag-mcp-gateway --profile company skill-review
ag-mcp-gateway --profile company skill-review ID
ag-mcp-gateway --profile company skill-approve ID
ag-mcp-gateway --profile company skill-discard ID
```

Опции `skill_router` — `max_bytes` для основного файла (по умолчанию 8 МиБ, минимум 128 КиБ), `cache_entries` (512) и `cache_ttl_seconds` (7 дней). Шлюз удаляет просроченный кэш и вытесняет старые записи при достижении лимитов. Черновики и утверждённые навыки сохраняются. Освобождённые страницы повторно используются, а SQLite может временно создать отдельный журнал транзакции. Настройка требует SQLite с FTS5.

## Поиск инструментов и оценки агентов

В профиле с токеном и включённым `management_bridge` задайте `"agent_discovery": true` и перезапустите шлюз. Команды доступны через тот же управляющий MCP Bridge.

| Команда | Назначение |
| --- | --- |
| `gateway_tools_search` | Найти инструменты и подходящие утверждённые навыки по `query`. `kind` выбирает `all`, `tools` или `skills`, `limit` ограничивает каждую группу. `backend` фильтрует инструменты. Для навыков включите `skill_router`. |
| `gateway_tool_describe` | Получить полные схемы входа и выхода, аннотации и метрики по полному имени `tool`. |
| `gateway_tool_rate` | Оставить оценку `useful: true/false` по `tool` после применения. Передайте уникальный `feedback_id` и повторите тот же ID при повторной отправке. |

Карточка возвращает `latency.mean_ms` и `latency.samples` для успешных вызовов через шлюз без присоединившихся singleflight-запросов. Окно содержит до 10 000 измерений на профиль. При запуске оно восстанавливается из последних 4 МиБ доступного журнала. При отсутствии измерений среднее равно `null`.

`usefulness.score` — доля полезных голосов от 0 до 1. Рядом возвращаются `helpful` и `votes`; без голосов оценка равна `null`. Поиск учитывает полезность при равной текстовой релевантности. Оценки хранятся в отдельной SQLite-базе профиля, а повторные отправки дедуплицируются по последним 4 096 ID. Это обратная связь агентов с доступом к Bridge. Голоса влияют только на порядок результатов при равной релевантности.

Та же карточка сигналов добавляется в `_meta["ag-mcp-gateway/discovery"]` обычного `tools/list`. Если клиент скрывает метаданные, их можно получить через поиск или описание.

## Модули данных и hooks

В профиле с токеном шлюза и включённым `management_bridge` задайте `"modules_enabled": true` и перезапустите процесс. На странице **Модули** можно сохранить определение, запустить его на JSON и привязать к MCP-инструменту до запроса или после ответа. Определения и привязки хранятся в `modules.json` выбранного профиля. Вход и результат ручного запуска в реестр не записываются.

Пример модуля считает сумму по полю `amount` и собирает результат в объект:

```json
{
  "id": "total",
  "title": "Сумма по строкам",
  "steps": [
    {"op": "aggregate", "source": "/input/rows", "item": "/amount", "method": "sum", "save_as": "sum"},
    {"op": "object", "fields": {"total": "/steps/sum"}}
  ]
}
```

В каждом шаге доступны исходные данные `/input`, результат предыдущего шага `/value` и именованные результаты `/steps/ИМЯ`. Для путей используется JSON Pointer. `select` выбирает значение, `object` собирает объект, `compare` показывает тип изменений и пути. `contains` и `filter` используют вложенное включение объектов и элементов массивов в стиле JSONB. `aggregate` поддерживает `count`, `sum`, `mean`, `min`, `max`. `math` принимает переменные, числа, скобки и операции `+ - * / %`. `call` доступен при ручном запуске, использует обычные политики шлюза и требует явного разрешения в `module_chain_tools` профиля и текущего признака read-only от MCP. Например, `"module_chain_tools": ["demo.echo"]` разрешает использовать тестовый echo. Можно выполнить до четырёх последовательных вызовов и собрать их результаты одним шагом `object`.

Ревизию и определения выдаёт `gateway_modules_list`. Команды Bridge `gateway_module_save`, `gateway_module_delete`, `gateway_module_bind` и `gateway_module_run` принимают `expected_revision`. В привязке задайте `tool`, `phase` (`before` или `after`) и `module`. Для снятия укажите `module: null`. Для запуска передайте `id` и `data`. Локальные модули можно переиспользовать в нескольких привязках. Чтобы удалить модуль, сначала снимите привязки.

Предварительный hook преобразует JSON-аргументы перед singleflight. Ошибка до отправки останавливает вызов. Постобработка получает структурированный JSON или один текстовый блок с JSON. Она сохраняет опубликованную схему результата. При ошибке после ответа шлюз сообщает, что upstream-вызов уже состоялся. Текущие привязки действуют на профиль в целом.

### Поколения временных hooks

Страница **Модули → Хуки и сессии** показывает поколение, закрепление, активные сессии и историю успешных применений. В настройках можно изменить оба порога. По умолчанию новый локальный шаблон получает **Gen3**, после **2** разных успешных сессий — **Gen2**, после **4** — **Gen1**. Повторы в одной сессии не увеличивают счётчик. Неактивные шаблоны удаляются через 1, 7 или 30 дней соответственно. Шаблон сохраняется, пока он закреплён, привязан на уровне профиля, активирован в открытой сессии или выполняется. Реестр ограничен 64 модулями, история — 16 успешными сессиями на хук.

Активация действует час либо до закрытия сессии. Откройте её на странице или через `gateway_hook_session_open`, затем привяжите модуль через форму либо `gateway_hook_activate`. Передайте выданный ключ только клиенту нужной сессии. Для stdio установите `AG_MCP_HOOK_SESSION` в окружении процесса клиента. Для прямого HTTP передайте ключ в `params._meta["ag-mcp-gateway/hook-session"]`. Следующая сессия получает свой ключ и явно активирует сохранённый модуль. Ключ остаётся в памяти шлюза. При перезапуске активные сессии завершаются, а определения и история сохраняются.

Смена шагов модуля сбрасывает историю его успешных применений. После изменения шагов, схемы инструмента или запрета требуется новая активация, даже если прежняя конфигурация вернулась. Сессионная привязка не перекрывает постоянный hook. История содержит случайные ID сессий и время первого успешного применения. Теги ACP или MCP служат для корреляции и не предоставляют доступ к сессионному hook. Управляющий Bridge с общим токеном позволяет открывать новые сессии, поэтому счётчик показывает сессии шлюза, а не отдельных людей.

## Метрики и журнал

- Входящие завершившиеся запросы, реальные upstream-вызовы, объединения, отказы и ошибки считаются раздельно. Дашборд показывает среднее и максимальное время входящего запроса с момента запуска.
- Пробная оценка токенов равна округлённому вверх числу UTF‑8 байтов JSON, делённому на четыре. Оценка не учитывает модель, системный промпт и токенизатор. Экономия байтов оценивает только сериализованные успешные ответы, которые шлюзу не пришлось повторно запрашивать у upstream.
- В `~/.ag-mcp-gateway/state/<profile>/logs` хранятся метаданные вызовов без аргументов, результатов и токенов. Для профилей со средой каталог имеет вид `state/.environments/<environment>/<profile>/logs`. Лимит по умолчанию — суммарно 50 000 000 байт на четыре сегмента. Параметр `log_max_bytes` задаёт общую квоту, каждый сегмент ограничен 50 000 000 байтами, поэтому четыре сегмента занимают не больше 200 МБ. При заполнении удаляется самый старый сегмент. Метрики сбрасываются при перезапуске, журналы остаются в пределах срока хранения.
- Автосбор инструментария работает при запуске и читает все страницы upstream-каталога до защитного лимита. Для обновления состава и восстановления подключения перезапустите профиль. Текущий срез передаёт `tools/list` и `tools/call`. Прогресс, ресурсы, промпты, входящие события и OAuth/SSO требуют отдельной интеграции.

### Подключение сборщика

На loopback-адресе запущенного профиля доступны три GET-эндпоинта. Для защищённого профиля сборщик передаёт действующий токен шлюза в `Authorization: Bearer …`. Используйте отдельный адрес для каждого профиля и держите токен в хранилище секретов сборщика.

| Маршрут | Что возвращает |
| --- | --- |
| `/api/diagnostics/v1/metrics` | JSON `service-diagnostics/v1`. Текущий и пиковый RSS, CPU в накопительных секундах user/system, uptime, размер журналов и суммарные MCP-счётчики. |
| `/api/technical-logs/v1/status` | Границы сохранённого журнала, квота, текущий курсор, состояние очереди и потери с момента запуска. |
| `/api/technical-logs/v1/events?limit=100` | Свежая страница `technical-logs-http/v1` из событий `technical-log/v1`. |

```sh
# GATEWAY_TOKEN предоставляет хранилище секретов сборщика.
origin=http://127.0.0.1:18792
curl -fsS -H "Authorization: Bearer ${GATEWAY_TOKEN}" "$origin/api/diagnostics/v1/metrics"
curl -fsS -H "Authorization: Bearer ${GATEWAY_TOKEN}" "$origin/api/technical-logs/v1/events?limit=100"
```

Для первоначальной загрузки читайте страницы назад через `journalEpoch` и `beforeSequence` из `nextCursor` до `hasMore=false`. Запомните `highWatermark` первой страницы. Затем опрашивайте журнал вперёд через `journalEpoch` и `afterSequence`, начиная с этой отметки и сохраняя `nextCursor` после приёма каждой страницы. При HTTP 409 зафиксируйте разрыв и возобновите сбор от `resetCursor` либо загрузите сохранившиеся страницы заново. События в каждой странице идут по возрастанию номера. Метрики и логи можно читать независимо.

Версии контрактов совпадают с ag-tasks. Для прямой регистрации в текущем Ag Observer его сборщик должен поддержать `application=ag-mcp-gateway`, передачу токена источника и выбор потоков technical/diagnostics. Шлюз публикует только эти потоки.

### Разбор ошибок агентом

При `management_bridge: true` агент может вызвать `gateway_read_errors` с фильтрами `backend`, `tool`, `trace_id` или `session_tag`. Если в ответе есть `next_cursor`, передайте его поля вместе с теми же фильтрами. `gateway_read_metrics` возвращает текущий срез счётчиков и ресурсов. Оба инструмента работают локально и не вызывают upstream MCP.

Технический журнал сохраняет запуск и остановку шлюза, изменения состояния и переподключения MCP, а также причины отказов и сбоев инструментов. Ошибка upstream классифицируется фиксированным кодом. В журнал попадают имя известного инструмента, профиль, задержка и, при наличии, trace ID и хеш сессии. Заголовки, учётные данные, аргументы и текст upstream-ошибок не записываются.

Файл `technical.sqlite3` находится рядом с журналом вызовов. Отдельная настройка профиля `technical_log_max_bytes` ограничивает основной файл SQLite. По умолчанию и максимально это 50 000 000 байт, допустимый минимум 65 536 байт. Ранее заданные значения больше 50 000 000 принимаются, фактический размер ограничивается 50 МБ. При заполнении старые записи удаляются. Кратковременный файл отката учитывается в `storage.journalBytes`. При переполнении очереди или недоступности записи счётчик `health.droppedTotal` показывает потери.

Настройка профиля `log_retention_days` задаёт срок хранения обоих журналов от 1 до 365 дней, по умолчанию 7. Шлюз проверяет срок при запуске и затем раз в минуту, в том числе в простое. Для технических событий учитывается время записи в SQLite, для сегментов вызовов — время последнего добавления в файл. Если очистка удалила нужную сборщику часть истории, следующий запрос со старым курсором получает HTTP 409.

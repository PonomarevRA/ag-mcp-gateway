# Работа агентов

[English](Agents.md) · [Главная](Home-ru.md)

1. Определите нужный профиль и среду из задачи. Выполните `ag-mcp-gateway --profile NAME status`. Проверьте состояние MCP и отсутствие ошибок входа или подключения.
2. Сгенерируйте настройку через `ag-mcp-gateway --profile NAME config codex`. Генератор поддерживает `codex`, `cursor`, `claude`, `opencode`, `deepseek` и `acp`. Добавьте фрагмент в соответствующий клиент. Порт в настройке должен совпадать с запущенным сервисом.
3. Прочитайте каталог через `tools/list` и продолжите по курсору. При включённом поиске используйте `gateway_tools_search`. Учитывайте назначение инструмента, схему, ожидаемую среду и политику.
    - `tools/list` сортирует по числу завершённых запросов с запуска профиля, исключая отказы политики. Для алфавитного порядка передайте `params._meta = {"ag-mcp-gateway/sort": "name"}` в первом запросе. Продолжайте по выданному курсору. Начните новый список, если курсор устарел после изменения каталога или вытеснения снимка.
    - В `gateway_tools_search` по умолчанию действует `sort: "usage"`. Также доступны `"relevance"` и `"name"`. Порядок применяется к найденным инструментам. Скиллы по-прежнему сортируются по релевантности.
4. Для управления используйте отдельное защищённое подключение MCP Bridge. Сгенерируйте его через `config --management codex` и начните с `gateway_inspect`. Для подключения действует тот же токен профиля. Изменения выполняются по разрешению оператора.
5. Для диагностики используйте `gateway_read_errors` по MCP, инструменту, trace ID или тегу сессии и `gateway_read_metrics` для метрик. После таймаута операции с побочным эффектом сначала проверьте фактическое состояние, затем решайте, нужен ли повтор.

При включённом реестре ищите подходы через `gateway_skill_search`. Выбирайте одобренную применимую запись и перепроверяйте политику перед повторением. Черновики проходят явную проверку. В реестре сохраняйте нейтральное описание и порядок инструментов. Автоматические хуки преобразуют JSON локально. В ручной цепочке могут вызываться только явно разрешённые инструменты чтения.

Стандартный вывод stdio-моста занят MCP-протоколом. Сервисный журнал открывайте отдельно либо читайте через `logs`. Для инцидента используйте идентификаторы и безопасные коды, сохраняя пароли, заголовки и ключи сессий в предназначенных для них хранилищах.

## Запуск локального MCP с Docker

Шлюз запускает команды stdio из профиля. Команду `docker` он распознаёт автоматически. Если Docker вызывает скрипт-обёртка, задайте `"requires_docker": true` в настройках этого MCP. Для обёртки проверка использует `docker` из её `PATH`. Если нужны `DOCKER_HOST` или `DOCKER_CONTEXT`, передайте их через `env_from`, чтобы проверка и MCP обращались к одному Docker Engine.

Вызовите `gateway_backend_startup_status` на основном MCP-адресе профиля. При `action: start_docker` запустите Docker или восстановите доступ к нему и обновите `tools/list`. Шлюз дождётся ответа Docker в фоне и запустит MCP из профиля. Управляющий `gateway_inspect` также показывает действие для восстановления. Если клиент кэширует список инструментов, обновите его или переподключите клиент после готовности MCP.

## Переиспользование цепочек MCP

Для предложенной цепочки Code Atlas `list_projects → search_nodes → describe_node` передайте в `gateway_module_run` только `data: {"project": "ag-design", "query": "Card"}`. Модуль выбирает проект по точному имени, берёт его ID и снимок, затем описывает первый найденный символ на снимке из результата поиска. Если проект не найден, имя неоднозначно или поиск не вернул символов, цепочка завершится до следующего вызова. Черновики для других интеграций по-прежнему принимают отдельные аргументы шагов.

Для пилота предложений задайте `"chain_suggestions": true` и `"modules_enabled": true` в профиле с защищённым управляющим MCP Bridge. Перечислите подходящие инструменты в `module_chain_tools`. Для каждого ручного прогона создавайте отдельный ID и передавайте `params._meta = {"ag-mcp-gateway/task-id": "routine-attempt-42"}` во всех вызовах этой задачи. Если ID задачи отсутствует, можно передавать общий W3C Trace ID. После двух совпадающих последовательных прогонов вызовите `gateway_chains_suggest` с именем первого инструмента цепочки. Проверьте черновик, сохраните его с текущей ревизией модулей и используйте предложенные `inputs`, если они есть. Для черновиков с `args_1`, `args_2` и т. д. передайте свежие аргументы и добавьте нужные связи между шагами.

Если по задаче видно, что одна и та же цепочка чтения или преобразования JSON будет нужна регулярно, сохраните её как модуль выбранного профиля. Сначала проверьте, есть ли подходящий модуль. Для разового запроса достаточно прямых вызовов. В профиле должны быть включены MCP Bridge и модули.

1. На `/manage/<профиль>` вызовите `gateway_modules_list`, чтобы получить определения и текущую ревизию. Если модуль уже подходит, используйте его.
2. Если модуля ещё нет и у агента есть разрешение на управление модулями, сохраните определение через `gateway_module_save`, передав `module` и `expected_revision`. Задайте параметры через `/input` и оставьте в определении только шаги и правила преобразования. Передавайте рабочие значения при запуске, а секреты получайте из настроенного хранилища профиля.
3. Сначала проверьте цепочку на тестовых данных. Вызовите `gateway_module_run` с `id`, `data` и текущей `expected_revision`. При конфликте ревизии перечитайте каталог и проверьте, что определение по-прежнему подходит. Для шагов `call` профиль должен явно разрешать инструмент в `module_chain_tools`, а MCP должен объявлять `readOnlyHint: true`. Шлюз выполняет до четырёх последовательных вызовов по обычной политике инструментов.

Для изменений политики вызовите `gateway_inspect`, затем `gateway_set_tool_policy` с текущей `expected_revision`. Сохранения из MCP Bridge и панели шлюза действуют для следующих вызовов в уже открытой сессии. После смены политики перечитайте `tools/list`, если клиент кэширует каталог.

Например, модуль `trace_search` принимает `trace_id`, подставляет его в параметры поиска Kibana и сервера логов и собирает ответы под ключами `kibana` и `logs`. Имена инструментов и аргументов берите из каталога профиля. Один вызов `gateway_module_run` выполнит оба поиска. Если первый источник вернёт ошибку, цепочка остановится.

Чтобы вызывать модуль из общего `/mcp/<профиль>`, откройте сохранённое определение на странице **Модули**, укажите обязательные поля ввода в разделе **Публикация в MCP** и нажмите **Опубликовать как инструмент чтения**. Для `trace_search` укажите `{"trace_id":"string"}`. В уже открытой сессии перечитайте `tools/list` и вызовите `trace_search` с `{"trace_id":"…"}`. В `structuredContent.result` будут ответы обоих источников. Для изменения опубликованного определения сначала снимите инструмент с публикации.

## Подключение к одному MCP

Скопируйте адрес Streamable HTTP из карточки MCP или поля `connections[].mcp_url` в выводе `status`. Для тестового MCP `docs` в профиле `company-test` со средой `test` адрес будет `http://127.0.0.1:18793/mcp/test/company-test/docs`. Ключ профиля здесь `test/company-test`, а `docs` — ключ в объекте `backends`. У профиля без среды ключ совпадает с его именем.

Для защищённого профиля передавайте токен шлюза как Bearer. Шлюз сам использует исходящие учётные данные и применяет общую политику, хуки и журналирование на обоих адресах. Каталог и вызовы по адресу отдельного MCP используют исходные имена, например `read_page`. В политике и журналах инструмент сохраняет имя `docs.read_page`. Общий каталог на `/mcp/test/company-test` также использует `docs.read_page`.

Для клиента со stdio сгенерируйте фрагмент подключения к этому серверу.

```sh
ag-mcp-gateway --profile company-test config --backend docs codex
```

Параметр `--backend` доступен для перечисленных выше клиентов. Управляющее подключение MCP Bridge создаётся отдельно с `--management`. Токен действует на весь профиль. Адрес определяет каталог и получателя вызовов, а полномочия задаются профилем и его политикой инструментов.

При включённом поиске агент может вызвать `gateway_tools_find_keywords` через MCP управления. Запрос `{"query":"grafana traceId"}` ищет по названиям MCP, описаниям и полям схем. Для ограничения одним MCP добавьте `"backend":"grafana"`. Ответ включает ключевые слова, наблюдаемые технические признаки и связанные запросы. Признаки извлекаются из имён полей успешных вызовов и структурированных ответов, исчезают через час без наблюдений или при перезапуске профиля и не содержат значений полей. В разделе **Инструменты** они загружаются при раскрытии «Ключевые слова».

Параметр `"draft_trace_module":true` запрашивает черновик модуля. Шлюз сопоставляет вход `trace_id` с полями совместимых инструментов чтения, разрешённых профилем. Перед сохранением через `gateway_module_save` проверьте сопоставление аргументов.
